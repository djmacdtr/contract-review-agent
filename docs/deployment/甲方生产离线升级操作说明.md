# 甲方生产离线升级操作说明

本说明是甲方生产环境后续应用升级的统一操作规范。适用于 openEuler/Linux x86_64、Docker Compose 部署，默认现有部署目录为 `/opt/contract-review/current`。

## 一、升级包组成

每次升级只上传以下三个文件到服务器同一目录，例如 `/root`：

```text
contract-review-agent-<release>-linux-amd64-offline-upgrade.tar.gz
contract-review-agent-<release>-linux-amd64-offline-upgrade.tar.gz.sha256
deploy_offline_upgrade.sh
```

其中：

- `*.tar.gz`：增量离线升级包，只包含新的业务镜像和生产部署文件；
- `*.sha256`：升级包外层 SHA-256 校验文件；
- `deploy_offline_upgrade.sh`：自动校验、解压并调用包内升级脚本的固定入口。

升级包不包含生产 `.env`、数据库数据、上传文件或历史报告。生产 `.env` 始终保留在服务器现有部署目录，不通过升级包覆盖。

## 二、升级前检查

选择维护窗口，确认没有 `PENDING` 或 `RUNNING` 任务后，以 `root` 用户执行：

```bash
cd /root
test -f /opt/contract-review/current/.env
test -f /opt/contract-review/current/compose.yaml
test -f /opt/contract-review/current/nginx.conf
docker info >/dev/null
docker compose -f /opt/contract-review/current/compose.yaml ps
```

不要打印 `.env` 内容，不要修改生产凭据。

## 三、一键升级

以下命令是唯一推荐入口，不要手动先解压或直接执行包内 `upgrade.sh`：

```bash
cd /root
sha256sum -c contract-review-agent-<release>-linux-amd64-offline-upgrade.tar.gz.sha256
chmod 0755 deploy_offline_upgrade.sh

bash ./deploy_offline_upgrade.sh \
  ./contract-review-agent-<release>-linux-amd64-offline-upgrade.tar.gz \
  ./contract-review-agent-<release>-linux-amd64-offline-upgrade.tar.gz.sha256
```

自动脚本依次执行：

1. 外层升级包 SHA-256 校验；
2. 临时目录解压；
3. 包内 `SHA256SUMS` 校验；
4. 业务镜像导入；
5. 备份现有 Compose、Nginx 和版本文件；
6. 执行 `alembic upgrade head`；
7. 重建 API/Worker 并启动服务；
8. 检查 `/health`、`/ready` 和服务状态。

部署目录不是默认路径时，显式传入环境变量：

```bash
CONTRACT_REVIEW_APP_ROOT=/实际部署根目录 \
  bash ./deploy_offline_upgrade.sh \
  ./contract-review-agent-<release>-linux-amd64-offline-upgrade.tar.gz \
  ./contract-review-agent-<release>-linux-amd64-offline-upgrade.tar.gz.sha256
```

## 四、升级后验收

```bash
cd /opt/contract-review/current

docker compose ps
docker image inspect contract-review-agent:<release> \
  --format '{{.RepoTags}} os={{.Os}} arch={{.Architecture}}'

curl -fsS http://127.0.0.1/health
curl -fsS http://127.0.0.1/ready
curl -fsS http://127.0.0.1/nginx-health

docker compose exec -T api alembic current
ss -lntp | grep -E ':(80|15432)\b'
```

验收要求：

- API、Worker、PostgreSQL、Nginx 均运行并健康；
- 镜像为 `linux/amd64`；
- Alembic 为 `0003_extraction_checkpoint (head)`；
- `/health`、`/ready`、`/nginx-health` 均成功；
- Nginx 对外监听 TCP 80；PostgreSQL 仅监听 `127.0.0.1:15432`；
- `.env`、数据库卷、上传文件和历史报告仍在。

通过基础验收后，再执行一项受控业务任务。失败时保留完整安全错误和日志，不重复创建任务。

## 五、回滚

每次升级脚本都会创建类似下列目录：

```text
/opt/contract-review/backups/before-<release>-<timestamp>/
```

升级失败时先停止后续操作，记录脚本输出和备份目录。确认回滚版本后执行：

```bash
BACKUP_DIR=/opt/contract-review/backups/before-<release>-<timestamp>
cp -a "$BACKUP_DIR/compose.yaml" /opt/contract-review/current/compose.yaml
cp -a "$BACKUP_DIR/nginx.conf" /opt/contract-review/current/nginx.conf
if [ -f "$BACKUP_DIR/RELEASE-VERSION.txt" ]; then
  cp -a "$BACKUP_DIR/RELEASE-VERSION.txt" /opt/contract-review/current/RELEASE-VERSION.txt
fi

cd /opt/contract-review/current
docker compose config --quiet
docker compose up -d
docker compose ps
```

不要删除新镜像、数据库卷或上传文件；旧镜像保留用于回滚。

## 六、禁止事项

生产升级过程中禁止执行：

```bash
docker compose down -v
docker volume prune
docker system prune
```

禁止覆盖服务器现有 `.env`，禁止清空 PostgreSQL，禁止删除上传文件和历史报告，禁止把真实凭据放入升级包或 Git。

## 七、发布端检查

发布端必须记录：

- Git 提交号；
- 镜像标签和 `linux/amd64` 信息；
- 升级包 SHA-256；
- 正式验收任务 ID；
- 测试结果和报告路径。

只有应用测试、镜像构建、包内外 SHA 校验和正式业务验收全部通过，才可把该版本作为新的生产基线。
