# 起草检查 KISS 交付架构收敛

日期：2026-08-27

## 决策背景

真实三文件任务已多次在 `FACT_EXTRACTION` 阶段因不同单批 LLM 输出问题失败。最新任务已经保存 `3` 条 profile、`96` 条 numeric 和 `24` 条 text checkpoint，仍因另一个单结构 text 批次返回 `LLM_INVALID_JSON` 而整体失败。

当前全量事实抽取需要约百次模型调用，并将任意一次 JSON、Schema 或证据校验失败升级为整任务失败。即使单次调用稳定率很高，端到端成功率也会随调用数量快速下降。该架构不符合当前“尽快完成甲方核心功能并部署验收”的目标。

## 交付范围

保留现有公开 API、任务队列、结果 Schema 和两个独立页面，不增加客户接口。

起草检查只交付以下核心能力：

1. 目标合同与模板的确定性文字差异、缺失和填写完整性检查。
2. 从目标合同及任意数量辅助资料中本地提取数值、金额、比例、日期、期限和带上下文的候选。
3. 对本地检索出的跨文件候选进行少量 LLM 语义判断，输出有双侧证据的冲突项。
4. 每个正式风险项提供一句 AI 建议；模型不可用时使用明确、专业的确定性 fallback。
5. 生成动态风险项和已完成检查对应的通过项；不使用固定合同类型清单，不做风险等级、人工复核、印章识别或报告文件生成。

## 简化工作流

```text
DOWNLOAD
  -> PARSE
  -> TEMPLATE_DIFF（本地确定性）
  -> REFERENCE_CANDIDATES（本地正则、归一化和上下文检索）
  -> CROSS_VALIDATE（少量批量 LLM，best effort）
  -> ADVICE（批量 LLM，失败使用 fallback）
  -> PAGE_ENRICH（只补正式结果涉及的位置）
  -> PERSIST
```

不再把 `DOCUMENT_PROFILE`、全量 `numeric/text` 事实抽取、全结构单元覆盖、事实评审、映射评审或语义规划作为交付主链路。现有复杂实现暂不删除，只从默认交付路径旁路，避免在交付前进行大规模清理。

## LLM 边界

- 不让 LLM 承担全文文字差异检测。
- 不要求 LLM 穷举整份文档的全部事实。
- 模型只消费本地筛选后的短候选及双侧上下文。
- 单任务 LLM 逻辑调用目标不超过 `10` 次，候选和建议均批量处理。
- JSON、Schema、证据回查或建议调用失败为软失败：丢弃无依据候选、记录现有 `warnings`，继续生成确定性结果。
- 任何未完成或被丢弃候选不得生成“校验通过”。

## 失败边界

仅以下情况使任务整体失败：

- 目标合同或模板无法下载、解析；
- 扫描件 OCR 整体失败且没有可比较文本；
- 所有辅助资料均无法解析，导致起草阶段完全无法执行跨资料检查；
- 数据库结果无法持久化。

单个辅助资料、单页、单候选或单次 LLM 失败应生成警告或风险项后继续；不得让一条模型幻觉或非法 JSON 阻断整份合同报告。

## 验收路径

1. 使用既定三份脱敏真实文件进行一次本机宿主 Worker 验收。
2. 验收要求：任务成功、控制台可见真实差异/通过项/页码/局部高亮/建议，LLM 调用不超过 10 次。
3. 再使用一组 DOCX 与盖章 PDF 完成 FINAL_COMPARE 验收。
4. 最后执行一次 Compose 冒烟与甲方服务器部署验证。

开发期间只运行变更相关测试；完整回归仅在两个核心流程均闭环后执行一次。

本记录为架构决策和交付范围收敛，不包含业务代码修改、外部调用或任务创建。
