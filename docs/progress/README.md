# 跨会话进度记录规范

## 1. 目的

本目录用于不同 Codex 会话之间传递已经完成的工作、真实验证结果、当前运行状态和下一步建议。

采用“每个重要任务新增一份记录”的方式，不使用多个会话共同覆盖单一状态文件，降低并行修改冲突和历史信息丢失风险。

## 2. 命名

```text
YYYYMMDD-HHmmss_<short-task-name>.md
```

- 时间使用 Asia/Shanghai，精确到秒。
- `<short-task-name>` 使用简短英文小写或数字加连字符，例如 `final-compare-slice`。
- 同名时增加 `-02`、`-03` 后缀。
- 不覆盖、重写或删除其他任务的历史记录。

## 3. 何时必须记录

- 开发新功能；
- 修复缺陷；
- 重构；
- 独立代码审查；
- 重要故障诊断；
- 数据库迁移；
- Docker/部署结构变化；
- 里程碑验收；
- 任务部分完成或被阻塞。

同一里程碑、同一会话或连续小迭代可以在阶段结束时合并为一份记录，不要求每个测试补充、文案修正或局部实现步骤单独生成进度文件。

以下纯运行操作没有产生代码、配置、数据库或重要诊断结果时可以不记录：

- 启动/停止服务；
- 查看状态；
- 查看日志；
- 打开控制台。
- 纯文案、格式和不影响行为的局部调整。

## 4. 开始任务前

1. 新会话只读取当前任务相关计划和最新一份相关进度/交接记录，不机械读取最近 3 份。
2. 检查 Git 状态，确认是否存在其他会话未提交修改。
3. 同一会话继续开发时，不重复读取未变化的文档。
4. 不假定历史记录中的计划已经完成，以当前代码和可重复验证结果为准。

## 4.1 测试记录粒度

- 日常小迭代默认记录定向测试，不要求每次重复 Docker 全量验收。
- 模块功能完成后记录相关单元和集成测试。
- 全量 pytest、Docker 构建、Alembic、健康冒烟和真实外部调用集中在里程碑、PR Ready、发布或交付验收时执行。
- 被延期的测试必须明确写为“未执行/待验收”，不能根据历史结果推定通过。

## 5. 进度文件模板

```markdown
# 任务进度：<任务名称>

## 基本信息

- 时间：YYYY-MM-DD HH:mm:ss +08:00
- 状态：COMPLETED / PARTIAL / BLOCKED
- 任务类型：BUILD / FIX / REVIEW / DIAGNOSE / TEST / DOCS
- 代码目录：D:\work\contract_review\contract-review-agent
- 当前分支：
- 当前提交：无提交时写 `UNBORN`
- 工作树状态：clean / dirty，并概括未提交范围

## 用户目标

用一段话记录本次用户要求。

## 本次完成

- 只列实际完成的工作。

## 修改文件

- 文件路径：修改目的

## 接口、数据和配置变化

- API：
- 数据库/迁移：
- 配置：
- 兼容性：

## 测试与验证

| 命令/检查 | 结果 | 关键数字或说明 |
|---|---|---|

## Docker 与运行状态

- API：
- Worker：
- PostgreSQL：
- 控制台：
- 最终是否保持运行：

## 重要决策

- 记录本任务形成、且未在正式设计文档中体现的决定。

## 已知问题与风险

- 只记录仍然存在的问题。

## 下一步建议

1. 按优先级列出。

## 下一会话首先阅读

- 列出关键文件和相关进度记录。

## 交接摘要

用不超过 10 行说明当前完成到哪里、最重要结果、服务状态和下一步。
```

## 6. 内容要求

- 记录实际执行的命令和结果，失败也要记录。
- 区分“完成”“未执行”“建议”，不能把计划写成完成。
- 说明是否修改业务代码、配置、数据库、Docker 服务和测试数据。
- 说明 Git 分支、提交和工作树状态。
- 使用相对仓库路径或绝对本地路径，确保下一会话能定位文件。
- 不记录 API Key、数据库密码、`.env` 全文、完整签名 URL、合同全文、无关终端输出或隐藏推理过程。
- 不自动提交进度文件；提交由用户或明确获授权的会话决定。
